# 设计模式规约

本文基于 **GoF 23 种设计模式**，说明在 **mdyaipay**（Java 17、Maven 多模块、领域分层）中**何时用、如何用、何时不用**。模式是手段，不是目标；优先满足 [`方便人理解代码规约.md`](方便人理解代码规约.md) 中的边界与依赖方向。

模块与分层见 [`modules.md`](modules.md)、[`detail-design.md`](detail-design.md)。

---

## 0. 总原则

| 原则 | 说明 |
|------|------|
| **接口在 domain，实现在 infrastructure** | 渠道、仓储等扩展点用接口 + 实现类，等价于 Strategy / Repository，不必再套一层「模式管理器」 |
| **构造注入，少用单例** | 应用服务、`Gateway` 实现由启动类或 DI 容器组装；避免静态 `getInstance()` 藏全局状态 |
| **枚举优先于纯 State 类** | 订单状态用 `PaymentStatus` + 聚合方法即可；仅当分支逻辑极重且需独立测试时再抽 State 对象 |
| **新增渠道 ≠ 改应用服务** | 新类实现 `PaymentGateway`（或代扣/代付网关），符合开闭原则，这是本工程最核心的扩展方式 |
| **模式要能在代码里指认** | 引入新模式时，在 PR 说明中写清「对应哪种模式、解决什么问题」；禁止为模式而模式 |

**与本工程已有结构的对应（不必再发明新名字）**

```text
Strategy + Adapter  →  PaymentGateway / MockPaymentGateway / 未来 UnionPayGateway
Repository          →  PaymentOrderRepository / MyBatis*
Facade              →  PaymentApplicationService（对外的用例门面）
Template Method     →  三类 *ApplicationService 中相似的「幂等 → 创建 → 调网关 → 持久化」可抽抽象基类（演进时）
```

## 1. 创建型模式（5）

### 1.1 单例模式（Singleton）

**意图**：保证全局唯一实例。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **谨慎** |
| 适用 | 无状态、进程级唯一且确无 DI 时（如极轻量的 ID 生成器配置） |
| 落点 | 优先在 `MdyaipayGatewayServer` / 启动类中 `new SnowflakeIdGenerator(...)` 并注入；不要新增 `SnowflakeIdGeneratorHolder.getInstance()` |
| 避免 | 单例里持有 `PaymentOrderRepository`、渠道客户端等有生命周期/可测试性问题的依赖 |

### 1.2 工厂方法（Factory Method）

**意图**：子类决定创建哪种产品。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **按需** |
| 适用 | 同一抽象产品、多种创建策略（如按 `channel` 选择不同 `PaymentGateway` 实现） |
| 落点 | `infrastructure` 包：`PaymentGatewayFactory.create(String channel)` 返回 `PaymentGateway`；domain 只依赖接口 |
| 避免 | 工厂里写支付编排或改订单状态 |

### 1.3 抽象工厂（Abstract Factory）

**意图**：创建一族相关对象（如「某渠道 SDK 的签名器 + HTTP 客户端 + 解析器」）。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **渠道集成复杂时推荐** |
| 适用 | 接入银联/网联等需成套组件的渠道包 |
| 落点 | `com.mdyaipay.payment.infrastructure.channel.xxx.XxxChannelFactory` 产出该渠道所需 Bean/组件 |
| 避免 | 用抽象工厂包装整个 `PaymentApplicationService` |

### 1.4 建造者（Builder）

**意图**：分步构造复杂对象，最终一致。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **参数多且可选字段组合多时推荐** |
| 适用 | 网银收单扩展（`bankCode`、`notifyUrl`、`frontReturnUrl` 等）、渠道请求报文、对账批次条件 |
| 落点 | domain 值对象：`OnlineBankingPaymentRequest.builder()`；或 tools 中与 HTTP 无关的纯 Java Builder |
| 避免 | 三个字段以内仍上 Builder；聚合根 `PaymentOrder` 核心构造保持简单构造器 + 工厂方法 |

### 1.5 原型（Prototype）

**意图**：通过复制已有实例创建新对象。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **少用** |
| 适用 | 配置模板、费率规则快照的深拷贝（财务/对账演进） |
| 落点 | 实现 `Cloneable` 或显式 `copy()` 的值对象；支付订单**禁止**用原型代替「新建聚合」 |
| 避免 | 用 clone 做幂等返回（幂等应查仓储返回同一实体） |

## 2. 结构型模式（7）

### 2.1 适配器（Adapter）

**意图**：将不兼容接口转换为调用方期望的接口。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **强烈推荐（渠道层）** |
| 适用 | 第三方 SDK / 旧 HTTP 接口适配为 `PaymentGateway`、`WithholdGateway`、`PayoutGateway` |
| 落点 | `infrastructure`：`UnionPayPaymentGatewayAdapter implements PaymentGateway` |
| 避免 | 在 `domain` 里 import 渠道 SDK 类型 |

### 2.2 桥接（Bridge）

**意图**：抽象与实现分离，可独立变化。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **与 Strategy 合并理解即可** |
| 适用 | 「产品类型（快捷/网银）」与「渠道实现」两维独立扩展时，用接口组合而非继承树爆炸 |
| 落点 | `PaymentProductType`（枚举）+ `PaymentGateway`（接口）由应用服务组合调用 |
| 避免 | 为每种「产品 × 渠道」建一个子类 |

### 2.3 组合（Composite）

**意图**：树形结构，统一对待叶子与容器。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **财务/分润演进时考虑** |
| 适用 | 结算规则树、分账条目树、菜单式收银台支付方式分组 |
| 落点 | `mdyaipay-finance` 或 `cashier` 未来包 |
| 避免 | 把 `PaymentOrder` 做成组合模式节点 |

### 2.4 装饰器（Decorator）

**意图**：动态叠加职责（日志、 metrics、重试）。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **横切关注点推荐** |
| 适用 | 包装 `PaymentGateway`：`RetryingPaymentGateway`、`MetricsPaymentGateway` 委托 inner |
| 落点 | `infrastructure`，构造函数接收 `PaymentGateway delegate` |
| 避免 | 装饰器内修改订单状态或吞掉业务异常 |

### 2.5 外观（Facade）

**意图**：为子系统提供简化入口。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **强烈推荐** |
| 适用 | 应用服务层即外观：`PaymentApplicationService` 对网关/编排隐藏仓储与网关细节 |
| 落点 | `application` 包；`MdyaipayGatewayServer` 只调应用服务，不直接调仓储 |
| 避免 | 一个 Facade 横跨 user + payment + accounting 全部逻辑（应按模块拆分 Facade） |

### 2.6 享元（Flyweight）

**意图**：共享细粒度对象以省内存。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **高并发热点配置时考虑** |
| 适用 | 渠道错误码表、银行编码表、不可变费率规则缓存 |
| 落点 | `mdyaipay-tools` 或各模块 `infrastructure.cache` |
| 避免 | 订单实例享元（每笔支付必须独立聚合） |

### 2.7 代理（Proxy）

**意图**：控制对真实对象的访问。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **按需** |
| 适用 | 远程渠道客户端延迟加载、访问控制、审计代理；与 Decorator 区别：Proxy 侧重控制访问 |
| 落点 | 渠道 HTTP 客户端包装层 |
| 避免 | 用动态代理隐藏核心业务规则（规则应在 domain / application） |

## 3. 行为型模式（11）

### 3.1 责任链（Chain of Responsibility）

**意图**：请求沿链传递，直到有处理者处理。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **网关与风控演进时推荐** |
| 适用 | HTTP 过滤器链：鉴权 → 限流 → 签名校验 → 路由；或代付前「风控 → 头寸 → 渠道」 |
| 落点 | `mdyaipay-gateway` 中间件；`payment` 应用层编排多个 `PaymentValidator` |
| 避免 | 链上每一环都改 `PaymentOrder` 状态且无顺序文档 |

### 3.2 命令（Command）

**意图**：将请求封装为对象，支持排队、撤销、日志。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **异步任务、批量代付/代扣时推荐** |
| 适用 | 「出款指令」「对账任务」入队；补偿查单任务 |
| 落点 | 独立 `command` 或 `task` 包 + 持久化任务表；命令只携带幂等键与参数 |
| 避免 | 把简单同步 `createAndPay` 强行包成 Command 而无队列需求 |

### 3.3 解释器（Interpreter）

**意图**：用语法树解释领域语言。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **不推荐默认使用** |
| 适用 | 极少数：可配置计费/分润公式 DSL（财务域） |
| 落点 | `mdyaipay-finance` 若确有规则引擎需求再引入 |
| 避免 | 用解释器实现普通 if-else 业务规则 |

### 3.4 迭代器（Iterator）

**意图**：顺序访问集合而不暴露内部结构。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **使用 Java 标准即可** |
| 适用 | `Iterable`、Stream 处理批次订单、对账明细 |
| 落点 | 仓储返回 `Stream<PaymentOrder>` 或分页对象，不必自研 Iterator 类 |
| 避免 | 为单次 `List` 遍历写自定义迭代器 |

### 3.5 中介者（Mediator）

**意图**：对象间通过中介通信，降低网状依赖。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **收银台编排时考虑** |
| 适用 | `cashier` 协调「会话、支付方式、payment 应用服务、用户签约」 |
| 落点 | `CashierSessionMediator`（命名示例），各参与者只依赖中介接口 |
| 避免 | 用 Mediator 替代清晰的 application 服务调用链 |

### 3.6 备忘录（Memento）

**意图**：保存/恢复对象历史状态。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **审计与回放演进时考虑** |
| 适用 | 订单状态变更快照、事件溯源（与「状态可审计」目标一致） |
| 落点 | 独立 `event` 或 `audit` 表，不要与聚合内存强耦合 |
| 避免 | 用 Memento 代替正规持久化与状态机 |

### 3.7 观察者（Observer）

**意图**：一对多依赖，状态变化通知订阅者。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **异步通知推荐** |
| 适用 | 支付成功 → 通知账务入账、商户回调、消息总线（规划） |
| 落点 | 领域事件 `PaymentSucceededEvent` + 监听器；或 Spring `@EventListener` / MQ 消费者 |
| 避免 | 在 `markSuccess()` 里直接写 JDBC 调账务（破坏模块边界） |

### 3.8 状态（State）

**意图**：对象行为随内部状态改变。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **默认用枚举 + 聚合方法；复杂时再抽** |
| 适用 | 当前 `PaymentOrder.markProcessing/markSuccess/...` 已是轻量状态机；若单状态转移逻辑超过数十行，可抽 `ProcessingState` 等 |
| 落点 | 优先 `PaymentStatus` 枚举 + `assertState`；State 类放在 `domain.state` 子包 |
| 避免 | 五个状态五个类，每类只有一行 `markSuccess` |

### 3.9 策略（Strategy）

**意图**：算法可互换。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **强烈推荐（已采用）** |
| 适用 | **`PaymentGateway` / `WithholdGateway` / `PayoutGateway`**；Mock 与真实渠道互换 |
| 落点 | 接口在 `domain`，策略实现在 `infrastructure`；应用服务构造注入 |
| 避免 | 用 if-else 按 channel 写死在 `PaymentApplicationService` 里 |

### 3.10 模板方法（Template Method）

**意图**：骨架在父类，步骤由子类实现。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **三类支付流程相似时推荐** |
| 适用 | 收单 / 代扣 / 代付共有的「幂等 → 创建 → PROCESSING → 调网关 → 落库」 |
| 落点 | 抽象类 `AbstractPaymentFlowService` 在 `application`，子类实现 `createOrder`、`invokeGateway` |
| 避免 | 模板方法里出现 HTTP 或 SQL；保持 application 层抽象 |

### 3.11 访问者（Visitor）

**意图**：在不改元素类的前提下增加新操作。

| 在本工程 | 建议 |
|----------|------|
| 推荐度 | **报表/导出/对账多维遍历时间考虑** |
| 适用 | 对多种单据类型做统一「导出 CSV」「生成对账行」 |
| 落点 | `finance` 模块；元素接口 `BillVisitable` + `ReconciliationVisitor` |
| 避免 | 为两三种类型硬上 Visitor，用 switch + 独立服务更简单 |

## 4. 模式 × 分层速查

| 分层 / 模块 | 优先模式 | 禁止 |
|-------------|----------|------|
| `domain` | State（轻量）、Strategy（接口定义） | Adapter 依赖 SDK、Singleton 全局仓储 |
| `application` | Facade、Template Method、Chain（校验） | 直接操作 JDBC / HttpClient |
| `infrastructure` | Adapter、Strategy（实现）、Decorator、Proxy、Abstract Factory | 改 domain 规则 |
| `gateway` | Facade（调 application）、Chain（过滤器）、Adapter（HTTP） | 订单状态机 |
| `mdyaipay-tools` | 无状态工具类、Flyweight（只读表） | 依赖 payment / gateway |

## 5. 引入新模式的流程

1. **问题一句话**：例如「新增渠道不能改 `PaymentApplicationService`」→ Strategy + Adapter。  
2. **对照上表**：确认推荐度不是「不推荐默认使用」。  
3. **落包**：接口进 `domain`，实现进 `infrastructure`，并在 [`detail-design.md`](detail-design.md) 补一节。  
4. **测试**：新策略/mock 可单测；应用服务用注入 mock gateway（现有测试即范例）。  
5. **文档**：PR 与 [`方便人理解代码规约.md`](方便人理解代码规约.md) 第 10 节同步设计文档。

## 6. 阅读检查清单

1. 新扩展点是否已是 **接口 + 实现**，而不是 switch-case 堆在应用服务里？  
2. 单例、静态全局是否必要？能否改为构造注入？  
3. 装饰/代理是否只做横切，不篡改业务状态？  
4. 状态机：枚举 + 聚合方法是否足够？State 类是否带来可读性收益？  
5. 模式名称是否在 PR / 文档中可指认，且与 [`modules.md`](modules.md) 依赖方向一致？

任一项答「否」或「说不清」，先简化设计再谈模式。
