# mdyaipay 概要设计

## 1. 背景与目标

`mdyaipay` 作为独立支付服务，负责订单支付链路的统一处理。通过统一的支付编排层，支持多支付渠道接入，降低业务系统与渠道强耦合。

支付能力在「资金方向」上分为：**收单入账**（快捷、网银等）、**协议代扣**（扣付款方）、**代付出款**（付收款方），三类流程在合规要素、状态机与时序上均有差异，需在领域层分型建模。

## 2. 设计原则

- 高内聚低耦合：领域规则集中在领域层，渠道适配放在基础设施层。
- 业务可扩展：新增渠道只需实现网关接口，不修改核心流程。
- 状态可审计：所有状态变化沉淀事件记录，支持追踪和回放。
- 接口幂等：同一业务单号重复请求不产生重复扣款/重复出款。
- 敏感数据最小化：卡号、证件等不落业务日志；代付收款方仅存令牌或内部户引用。

## 3. 总体架构

### 3.1 Maven 多模块

平台按业务能力拆分为子模块（父工程聚合构建）：

- **用户（mdyaipay-user）**：主体与权限。
- **账务（mdyaipay-accounting）**：分录与余额。
- **财务（mdyaipay-finance）**：结算与对账。
- **支付（mdyaipay-payment）**：收单订单与渠道编排。
- **网关（mdyaipay-gateway）**：对外流量接入与管控（「网管」入口）。
- **收银台（mdyaipay-cashier）**：下单与支付方式编排。

模块边界与典型调用关系见 `docs/modules.md`。

### 3.2 支付子模块内分层

支付核心仍采用经典四层：

- 接口层（Interface）：未来承载 REST API、RPC、消息入口。
- 应用层（Application）：编排支付流程，调用领域服务。
- 领域层（Domain）：定义支付订单、状态机、领域规则。
- 基础设施层（Infrastructure）：实现仓储、支付渠道适配器、日志落库。

### 3.3 支付产品分型（能力视图）

| 能力 | 典型场景 | 领域聚合 | 渠道网关抽象 |
|------|----------|----------|----------------|
| 快捷/条码收单 | C 端即时到账展示 | `PaymentOrder` + `PaymentProductType.QUICK_COLLECTION` | `PaymentGateway` |
| 网银 | 跳转银联网关、B2C/B2B | `PaymentOrder` + `PaymentProductType.ONLINE_BANKING` | `PaymentGateway`（异步确认为主） |
| 代扣 | 周期性扣费、信贷还款 | `WithholdOrder` | `WithholdGateway` |
| 代付 | 结算打款、提现 | `PayoutOrder` | `PayoutGateway` |

签约与授权（代扣前置条件）属于用户/合规子域，落在 **用户模块** 或与渠道签约中心对接；支付模块通过 `agreementNo` 等引用关联。

## 4. 核心业务流程

### 4.1 收单（快捷）

1. 业务系统提交支付请求（订单号、金额、渠道、`QUICK_COLLECTION`）。
2. 应用层幂等与参数校验。
3. 创建 `PaymentOrder` 并持久化，`PROCESSING`。
4. 调用 `PaymentGateway.pay()`。
5. 同步或短时轮询得到结果，更新 `SUCCESS` / `FAILED`。
6. 异步通知账务入账（规划）。

### 4.2 网银

1. 提交收单请求（订单号、金额、渠道、`ONLINE_BANKING`，以及扩展字段：银行编码、前台跳转 URL、客户端类型等，详见详细设计）。
2. 创建订单并置 `PROCESSING`。
3. 调用渠道「下单」接口，`PaymentGateway.pay` 返回 `AWAITING_CHANNEL_CONFIRMATION`，订单保持 `PROCESSING`；返回跳转 URL 或表单信息给收银台。
4. 用户完成银行侧支付后，依赖渠道 **异步通知 + 主动查单** 双保险；网关验签后调用 `confirmChannelPayment`（或领域等价接口）落到 `SUCCESS` / `FAILED`。
5. 驱动账务入账。

### 4.3 代扣

1. 校验协议状态（用户模块或签约服务）。
2. 业务传入商户扣款单号、协议号、金额、渠道。
3. 创建 `WithholdOrder`，幂等键为扣款单号。
4. `WithholdGateway.deduct()` 调用渠道；支持异步通知补状态。
5. 成功后触发账务扣减与流水。

### 4.4 代付

1. 业务传入商户出款单号、金额、收款方引用（令牌）、渠道。
2. 创建 `PayoutOrder`，幂等键为出款单号。
3. `PayoutGateway.remit()`；常见为异步到账，需查单与回调对齐。
4. 成功后更新内部头寸与对账批次（财务模块）。

## 5. 非功能设计

- 性能目标：单机每秒 200+ 创建支付请求（示例目标）；代付批量通道需单独限流与队列。
- 可用性：异常时不丢失状态迁移记录；网银/代付依赖消息补偿与查单。
- 安全性：敏感字段不明文日志输出；网联/银联类报文按渠道规范加密签名。
- 可运维：关键节点埋点和结构化日志输出；渠道错误码映射统一。

## 6. 扩展规划

- 退款、撤销、关单与部分成功批次。
- 异步回调验签、防重放与重试退避。
- 消息总线与账务、财务的最终一致性。
- 批量代扣、批量代付任务编排。
