# 方便人理解代码规约

目标：让半年后的自己、同事或 AI 打开文件后，**不用猜**就能回答三件事：这段代码做什么、怎么用、依赖什么。

本规约服务于阅读，不替代编译器、Checkstyle 或格式化工具。能编译只说明机器能跑；能读懂才说明人能改。给人看的说明用简体中文（见第 4 节），标识符仍用完整英文。

适用范围：**mdyaipay** Maven 多模块工程（Java 17）。模块边界与职责见 [`modules.md`](modules.md)；领域与接口细节见 [`detail-design.md`](detail-design.md)。

**强制级别（MANDATORY）**：本规约为仓库编码的强制标准，不是可选风格指南。新功能、重构、Bug 修复在 **同一次提交** 内须满足下文 §3.1、§4、§12；AI 与人工贡献均须遵守。Cursor 持久规则：[`.cursor/rules/java-chinese-readable-docs.mdc`](../.cursor/rules/java-chinese-readable-docs.mdc)（`alwaysApply: true`）。审查时未补全中文 Javadoc / 功能块的 diff 应退回。

## 1. 先写清边界

一个文件、一个类型只承担一件读者能用一句话说清的职责。

| 好的边界 | 难读的边界 |
|----------|------------|
| `PaymentApplicationService` 只编排收单流程 | 一个类里同时写 HTTP 解析、订单状态机、Mock 渠道 |
| `PaymentOrder` 只管收单聚合与状态迁移 | 在网关 Handler 里直接改 `PaymentStatus` |
| `MoneyUtils` 只做分/元与金额校验 | 各模块复制 `amount <= 0` 判断 |
| `SnowflakeIdGenerator` 只生成 ID | 在业务类里内嵌雪花位运算 |

判断标准：

- 不看实现，也能从类型名知道它做什么。
- 改内部算法，调用方不必跟着改。
- **单个 public 类型不超过 1000 行**（含空行与注释）。接近上限时按职责拆类，禁止继续堆方法。
- 文件变大时，优先按**业务职责**拆，而不是机械拆「技术层」；同一职责拆成多个小类时，每个类仍须能一句话说清。

### 1.1 何时拆类型

| 信号 | 拆法 |
|------|------|
| 改收单必须翻过代付代码 | 按**产品能力**拆：`PaymentApplicationService` / `WithholdApplicationService` / `PayoutApplicationService` |
| 聚合根与仓储接口混在一起 | 领域实体在 `domain`，持久化在 `infrastructure` 实现 `*Repository` |
| HTTP 路由与支付编排写在同一巨型类 | 网关只解析请求、调应用服务；规则留在 `mdyaipay-payment` |
| 渠道适配与订单规则耦合 | 渠道实现 `*Gateway`，Mock 放在 `infrastructure`，不污染 `domain` |
| 无状态算法被多处复制 | 抽到 `mdyaipay-tools-common` 或领域内的 `final` 工具类，不要空壳 `Manager` |

不要拆的情况：只有几个字段的 DTO、仅为一个类服务且不足一屏的 `private` 方法、还说不清职责的「Utils2 / Helper / CommonService」。

### 1.2 何时拆模块、包与文件

**Maven 模块（artifact）**

| 模块 | 职责一句话 |
|------|------------|
| `mdyaipay-tools` | 公共 Maven 聚合（`packaging=pom`），子模块见 `common` / `timetrace` / `loadtest` |
| `mdyaipay-tools-common` | 横切工具与统一模型（ID、金额、错误码、`ApiResponse`），**不依赖**任何业务子模块 |
| `mdyaipay-tools-loadtest` | 压测 Maven 聚合：`core` + HTTP/Dubbo/Spring Cloud 驱动 + CLI，**不依赖** payment 等业务模块 |
| `mdyaipay-tools-loadtest-core` | 场景模型、压测引擎、指标采集与报告导出；协议实现通过 `LoadTestDriver` SPI 扩展 |
| `mdyaipay-user` / `accounting` / `finance` | 各自领域，按需演进 |
| `mdyaipay-payment` | 收单、代扣、代付领域与应用编排 |
| `mdyaipay-gateway` | 对外 HTTP 接入、路由，调用 payment 等 |
| `mdyaipay-cashier` | 收银台会话与支付方式编排 |

- **新能力先问「属于哪个已有模块」**；只有现有模块一句话概括不了时，才新增子模块，并更新 [`modules.md`](modules.md) 与父 `pom.xml`。
- 依赖单向：`tools` 无上游业务依赖；`gateway` / `cashier` 可依赖 `payment` 等，**`payment` 的 domain 不得依赖 gateway**。
- 禁止把各模块的杂项扔进无边界包名；跨模块复用放 **`mdyaipay-tools-common`**，模块内复用放该模块合适子包。

**包结构（以 payment 为准，其他模块对齐）**

```text
com.mdyaipay.<module>
├── application          # 应用服务：编排、幂等、调 domain + gateway 接口
├── domain               # 聚合、枚举、仓储与网关 *接口*
└── infrastructure       # 仓储实现、Mock/真实 *Gateway* 适配器
```

`mdyaipay-payment` 在以上三层下再按能力分子包：`collect`（收单）、`withhold`（代扣）、`payout`（代付），见 [`detail-design.md`](detail-design.md) §1。

- **一个文件一个 public 主类型**，文件名与类名一致（如 `PaymentOrder.java` → `PaymentOrder`）。
- 同一能力下 **3 个及以上** 主类型时，用子包（如 `com.mdyaipay.tools.id`、`com.mdyaipay.tools.money`）。
- 模块根包用 **`package-info.java`** 写一句模块职责（现有各模块已有先例）；不在每个源码目录复制 `功能说明.md`，长期设计放在 `docs/`。

依赖方向（新增引用不要逆行）：

```text
mdyaipay-gateway / mdyaipay-cashier
        ↓
mdyaipay-payment（及未来的 user / accounting / finance）
        ↓
mdyaipay-tools-common / mdyaipay-tools-timetrace / mdyaipay-tools-loadtest（聚合于 mdyaipay-tools）
```

## 2. 名字说人话

名称要让读者读出**支付业务含义**，不要读出实现细节。

**类型与文件**

- 用完整英文词：`PaymentProductType`、`WithholdOrder`，不要 `PPT`、`WHOrd`。
- 文件名与 public 类名一致。
- 无状态工具用 `final` 类 + 私有构造（如 `MoneyUtils`），或纯静态方法类。
- 接口表能力：`PaymentGateway`、`PaymentOrderRepository`；实现带介质前缀：`MyBatisPaymentOrderRepository`、`MockPaymentGateway`。

**方法与字段**

- 动词 + 对象：`createAndPay`、`confirmChannelPayment`、`markProcessing`、`findByOrderNo`。
- 布尔用是非判断：`success`（参数）、状态用枚举 `PaymentStatus`，不要 `statusFlag == 1`。
- 幂等键在名字里体现：`orderNo`、`deductionNo`、`payoutNo` 与 [`detail-design.md`](detail-design.md) 一致。

**统一产品词汇（全仓库一致）**

| 概念 | 推荐命名 |
|------|----------|
| 收单 | `PaymentOrder`、`PaymentApplicationService` |
| 快捷 / 网银 | `PaymentProductType.QUICK_COLLECTION` / `ONLINE_BANKING` |
| 代扣 | `WithholdOrder`、`agreementNo`、`deductionNo` |
| 代付 | `PayoutOrder`、`payoutNo`、`payeeRef` |
| 金额（内部） | `long` **分**；元换算用 `MoneyUtils` |

**避免**

- `data`、`info`、`helper`、`manager2`、`doStuff`。
- 同一概念两个名字（例如 HTTP 字段 `orderId` 与领域 `orderNo` 混用且无映射说明）。

## 3. 控制流要直

人按从上到下读。把「先失败、再干活」写清楚。

```java
// 好：入口处拦住，后面是正常路径
if (amount <= 0) {
    throw new IllegalArgumentException("amount must be greater than 0");
}
PaymentOrder existed = orderRepository.findByOrderNo(orderNo).orElse(null);
if (existed != null) {
    return existed;
}
```

```java
// 差：深层嵌套，读者要在脑子里记分支
if (orderRepository.findByOrderNo(orderNo).isPresent()) {
    if (orderRepository.findByOrderNo(orderNo).get().getAmount() > 0) {
        // ...
    }
}
```

约定：

- 参数与前置条件不合法时 **提前 throw** 或 **提前 return**（幂等命中直接返回已有单）。
- 对枚举状态用 `switch` 写全已知 case；新增枚举值时编译器应能提醒补分支。
- 一个方法只做一种抽象层次：应用服务编排步骤，聚合根只做状态迁移，网关只做渠道调用。
- public API 放在类上部，`private` 辅助方法放在下面。

### 3.1 复杂方法：按功能块分段并写中文块说明

**适用**：单方法内有多步业务编排、分支或持久化，读者需要**扫一眼结构**再读细节。典型场景：`application` 层 public 方法、网关 Handler 内编排、渠道适配里「组报文 → 签名 → 发送 → 解析」等。

**不适用**：不足一屏的 getter/校验、聚合根内单一状态迁移、工具类一两行封装。此时块注释只会增加噪音（见第 4 节）。

**功能块** = 方法内**连续、只做一件事**的一段语句；块与块之间用**空行 + 中文块说明**隔开，说明写**业务意图**（「做什么、为什么在这一步做」），不逐行翻译代码。

#### 写法（推荐格式）

块说明用**单独一行的块注释**（`/* … */`），放在该块**第一行可执行语句之前**；块标题用简短名词短语，与支付域词汇一致：

```java
public PaymentOrder createAndPay(String orderNo, long amount, String channel, PaymentProductType productType) {
    /* 功能块：产品与金额前置校验 — 非法请求在此失败，不创建订单 */
    if (productType != PaymentProductType.QUICK_COLLECTION && productType != PaymentProductType.ONLINE_BANKING) {
        throw new IllegalArgumentException("productType must be QUICK_COLLECTION or ONLINE_BANKING");
    }
    MoneyUtils.requirePositiveFen(amount);

    /* 功能块：幂等 — 商户单号已存在则直接返回，不再调渠道 */
    PaymentOrder existed = orderRepository.findByOrderNo(orderNo).orElse(null);
    if (existed != null) {
        return existed;
    }

    /* 功能块：创建订单并置为处理中 — 持久化后再调网关，便于查单与对账 */
    PaymentOrder order = new PaymentOrder(orderNo, amount, channel, productType);
    orderRepository.save(order);
    order.markProcessing();
    orderRepository.save(order);

    /* 功能块：渠道受理 — 按同步结果更新终态；网银保持 PROCESSING 等回调 */
    try {
        PaymentSubmitResult result = paymentGateway.pay(order);
        switch (result) {
            case SYNC_SUCCESS -> order.markSuccess();
            case SYNC_FAILURE -> order.markFailed();
            case AWAITING_CHANNEL_CONFIRMATION -> { /* 保持 PROCESSING */ }
        }
    } catch (RuntimeException ex) {
        order.markFailed();
    }

    /* 功能块：落库并返回 — 调用方看到的是最新状态 */
    return orderRepository.save(order);
}
```

#### 功能块划分原则

| 原则 | 说明 |
|------|------|
| **一块一事** | 一块内不要混「校验 + 调渠道 + 改状态」；读者应能用块标题当小目录。 |
| **顺序即故事** | 与应用服务常见链路一致：前置校验 → 幂等 → 建单/改状态 → 外部调用 → 终态与持久化 → 返回。 |
| **标题说业务** | 用「幂等」「渠道受理」「落库」等域内词；避免「第一步」「处理数据」「逻辑块 1」。 |
| **说明写 why** | 块注释补规则或例外（如网银为何保持 `PROCESSING`）；块内 obvious 的 if 不必再写行尾注释。 |
| **块不宜过大** | 单块超过约 **25 行**或出现第二层业务分支时，优先抽 `private` 方法，方法名即块标题，原位置可留一行 `/* 功能块：… — 见 xxx() */` 或删块注释改读方法名。 |
| **块不宜过碎** | 不要每个赋值一行块说明；两行校验合并为「前置校验」即可。 |

#### 与方法 Javadoc、private 方法的关系

- **方法 Javadoc**（第 4 节）：整方法对外的契约（做什么、幂等、前置条件）。
- **功能块说明**：方法**内部**阅读地图；改块顺序或增删块时，同步检查 Javadoc 是否仍准确。
- 块被抽成 `private` 方法后：块注释可省略，由方法名 + 必要 Javadoc 承担；public 入口方法仍建议保留块注释标出「幂等 / 渠道 / 落库」等主阶段。

#### 反例

```java
// 差：无块结构，80 行从上到下只有零散的 //
// 差：块标题是技术步骤而非业务 — 「功能块：调用 repository」
// 差：块说明重复方法 Javadoc 全文
// 差：块与块之间无空行，块注释写在方法体最末尾
```

#### 审查时自问

1. 闭掉方法体，只看块注释，能否复述一遍业务流程？
2. 任一块是否混合两种以上业务职责？
3. 新增分支是否落在正确的块内，还是应新开一块或抽方法？

## 4. 注释用中文，写「为什么」，不写「又说了一遍代码」

标识符保持英文。**给人看的 Javadoc、`//`、块注释 `/* */` 用简体中文**；必须引用外部协议原文时（渠道错误码、JSON 字段名）可保留英文片段。

### 4.1 注释粒度（Java / mdyaipay）

| 对象 | 要求 |
|------|------|
| 模块 | `package-info.java` 或子模块 `pom.xml` 的 `<description>`：一句话职责 |
| public 类 / 接口 / 枚举 / 注解 | 类上方 Javadoc：职责 + 易混淆的「不负责什么」 |
| 对业务模块暴露的 public 方法 | Javadoc：做什么、前置条件、副作用；支付域补充幂等语义 |
| 仅模块内使用的类型 / 方法 | 至少类级 Javadoc；方法可用简短 Javadoc 或配合 §3.1 功能块 |
| 复杂方法体（见 **§3.1**） | 块首 `/* 功能块：… */`，**不**要求每行行尾 `//` |
| 非显而易见的分支 | 行内 `//` 或块注释：规则与例外 |
| AspectJ 空 pointcut 方法 | 方法上一行 Javadoc 说明「匹配谁、排除谁」，避免读者翻 pointcut 表达式 |
| 注解属性 | 每个属性单独 Javadoc：默认值含义及对运行时的影响 |

**不强制**给每一行可执行语句加行尾 `//`（避免注释噪音）。**强制** public 表面、注解属性、复杂编排与 §3.1 功能块可追踪。

新代码或改动文件时：**同一次提交**内补全该文件新增/变更 API 的 Javadoc；改行为时在注释里写清规则变化。

### 4.2 横切与工具库（以 `mdyaipay-tools-timetrace` 为参照）

框架型代码没有「收单 / 幂等」等业务词，功能块标题用**技术意图**即可（如「会话初始化」「嵌套入口短路」），仍须中文、仍须写 **why**：

| 层次 | 注释重点 |
|------|----------|
| `@TimeTrace` | 类/方法/类级注解差异；`reportThresholdMillis` 与异常时是否绕过阈值 |
| `TimeTraceAspect` | Spring AOP 入口 advice；`TimeTraceEntrySupport` 负责会话与报告 |
| `TimeTraceAutoConfiguration` | Boot 自动注册切面（需 `spring-boot-starter-aop`）；`mdyaipay.timetrace.enabled` |
| `TimeTraceContext` | ThreadLocal 会话、栈与树的关系；`enterFrame` / `leaveFrame` 契约 |
| `TimeTraceReport*` / `TimeTraceListener` | 报告字段含义、Listener 触发条件 |
| `sample` 包 | 标明仅单测/本地验证，不参与业务模块 |

完整范例见：`mdyaipay-tools/mdyaipay-tools-timetrace/src/main/java/com/mdyaipay/tools/timetrace/`。

**压测工具库（以 `mdyaipay-tools-loadtest` 为参照）**

与 TimeTrace 类似，无收单/幂等业务词；功能块标题用**压测意图**（预热、正式阶段、Ramp-up、采样、导出）。设计细节见 [`loadtest-design.md`](loadtest-design.md)。

| 层次 | 注释重点 |
|------|----------|
| `LoadTestDriver` SPI | 只负责**单次**请求/调用；并发与时长由引擎统一调度，驱动内不要自建线程池 |
| `LoadTestEngine` | 预热不计入报告、正式阶段 wall time 算 TPS；`Ctrl+C` 与 shutdown hook 的语义 |
| `LoadProfile` / `MetricsProfile` | 各字段对调度与分位数的影响；`targetRps` 与 `threads` 的配合 |
| `ScenarioParser` / `PlanOverrideApplier` | YAML/JSON 与 CLI `--load.*` 覆盖的优先级 |
| `MetricsCollector` / `LatencyReservoir` | 样本上限与近似分位数；错误采样防 OOM |
| `CompositeReportExporter` | 各 `formats` 输出位置与 CI 可读 JSON 字段 |
| `*-http` / `*-dubbo` / `*-springcloud` | `target` 必填键、成功判定规则；**不负责**压测编排 |
| `LoadTestCliMain` | 仅对授权环境施压的警告；退出码含义 |

完整范例见：`mdyaipay-tools/mdyaipay-tools-loadtest/` 下各子模块 `src/main/java`。

### 4.3 不该写的注释

```java
// 遍历订单  ← for 已经说明在遍历
orderRepository.save(order); // 保存订单
```

### 4.4 好的例子（业务 + 横切）

```java
/**
 * 收单应用服务：快捷与网银的创建、渠道调用与（网银）异步确认。
 * 代扣、代付请使用 {@link WithholdApplicationService}、{@link PayoutApplicationService}。
 */
public class PaymentApplicationService { ... }

/**
 * 报告输出的最低耗时门槛（毫秒）。{@code 0} 表示不限制。
 * 大于 {@code 0} 时仅当入口总耗时达标才回调 {@link TimeTraceListener}；异常结束不受阈值限制。
 */
long reportThresholdMillis() default 0L;

/* 功能块：嵌套 @TimeTrace — 已在追踪栈内时不再开新会话，但仍计帧写入调用树 */
if (TimeTraceContext.isTracing()) {
    return TimeTraceNestedSupport.aroundNested(joinPoint);
}
```

会话内其它 `@Service` / `@Repository` 等 Bean 的 public 方法由 `TimeTraceAspect` 的 nested 切点计帧，无需再标 `@TimeTrace`。
```

## 5. 状态从哪来、到哪去，要一眼能追

支付链路里状态与幂等最容易散。读者必须能顺着一条线走：

1. 商户请求 → **网关** 解析 JSON → **应用服务** 幂等校验（`orderNo` / `deductionNo` / `payoutNo`）。
2. 应用服务 → 创建聚合 → `markProcessing` → 调 `*Gateway` → 更新终态或保持 `PROCESSING`（网银）。
3. 渠道回调 → **网关** 验签（规划）→ `confirmChannelPayment` → 领域状态迁移 → 仓储持久化。

约定：

- 订单状态**只通过聚合根方法**变更（`markSuccess` 等），不要在网关里直接 `setStatus`。
- 幂等「已存在则返回」只在**应用服务入口**做，仓储不负责业务幂等语义。
- 金额单位：**内部 long 分**；校验优先 `MoneyUtils.requirePositiveFen`（逐步统一），与 [`detail-design.md`](detail-design.md) 一致。
- 错误码与 HTTP 包装：复用 `mdyaipay-tools-common` 的 `ErrorCode`、`ApiResponse`（网关演进时统一，避免每个 Handler 一套 JSON）。

## 6. 接入层与领域分开读

读者打开 `MdyaipayGatewayServer`，应看到「路由、读 body、调应用服务、写 JSON」。领域规则在 `mdyaipay-payment`。

| 放在 gateway | 放在 payment |
|--------------|--------------|
| 路径、HTTP 方法、状态码 | 幂等、产品类型校验、状态机 |
| Jackson 解析 / 序列化 | `PaymentGateway` 渠道抽象 |
| 端口与环境变量 | `PaymentOrder` 行为与不变量 |

- 渠道回调入口归属 **gateway**，验签后调用应用服务（见详细设计 2.7、2.8 节）。
- 敏感字段（卡号、明文账号）不进日志；代付只用 `payeeRef` 等令牌（见概要设计原则）。

---

## 7. 数据形状保持稳定、可见

对外协议（HTTP JSON、商户单号、金额单位）改动成本高，读者需要看见「哪些不能随便改」。

- 对外 API 路径与字段以 [`detail-design.md`](detail-design.md) 第 2.8 节为基准；变更须同步文档与测试。
- 枚举状态机：非法迁移在聚合内拒绝，终态不可再变（见 `PaymentOrder`）。
- 新增 `PaymentProductType` 或状态枚举值时，补全 `switch`、测试与文档。
- 演示用内存仓储可替换为 JDBC 等，但 **仓储接口**（`PaymentOrderRepository`）保持稳定。

---

## 8. 测试是给人看的说明书

测试类放在对应模块的 `src/test/java`，包名与主代码一致。

好的例子：

- `createAndPay_whenDuplicateOrderNo_returnsExistingOrder`
- `confirmChannelPayment_rejectsNonOnlineBankingProduct`
- `generatesUniqueIds`（tools 模块）

约定：

- 一个测试方法主要证明一件事；名字用行为描述，不要 `test1`。
- 断言面向可观察结果（状态、金额、返回单号），不断言 private 步骤。
- 改产品规则时**先改测试名与断言**，让失败信息指向业务语义。
- 全量验证：在工程根目录执行 `mvn clean test`（见 [`modules.md`](modules.md)）。

## 9. 设计文档放在 `docs/`

长期文档集中在 **`javaproject/mdyaipay/docs/`**，不在仓库根目录堆 `.md`（根目录 [`README.md`](../README.md) 除外）。

| 文档 | 放什么 |
|------|--------|
| [`overview-design.md`](overview-design.md) | 背景、原则、能力分型、非功能 |
| [`detail-design.md`](detail-design.md) | 包结构、领域模型、应用服务、HTTP 接口 |
| [`modules.md`](modules.md) | Maven 模块职责与依赖 |
| [`方便人理解代码规约.md`](方便人理解代码规约.md) | 本文件：怎么写让人读懂的代码 |
| [`设计模式规约.md`](设计模式规约.md) | GoF 23 种模式：何时用、落在哪一层 |

新增专题 spec 可放在 `docs/` 下子目录；稳定后把结论收进上表四份之一，避免文档分叉。

## 10. 改代码必须同步改设计文档

行为、HTTP 契约、模块职责或包结构一变，**同一次提交**里更新对应 `docs/` 文档。禁止先合代码、文档「过后再补」。

| 改了什么 | 必须同步 |
|----------|----------|
| 新模块 / 模块职责 | [`modules.md`](modules.md)、父 `pom.xml`、根 [`README.md`](../README.md) |
| 领域模型、状态机、应用流程 | [`detail-design.md`](detail-design.md) |
| 能力边界、产品分型 | [`overview-design.md`](overview-design.md) |
| 编码约定本身 | 本规约 |

纯格式化、与文档描述无关的重命名：文档未说错则可不改；**文档里任一句会过时就必须改。**

提交说明写清「改了哪条业务规则」，不要只列文件名。

---

## 11. 少即是清晰

不要为「将来可能」增加读者必须跳过的代码。

- 不需要的接口、泛型、配置 DTO 一律不写。
- 不复制第二套幂等或金额校验；抽到应用服务或 `mdyaipay-tools-common`。
- 不在修收单时顺手重构代付；无关 diff 会让审查找不到真正变更。
- 新渠道：实现现有 `*Gateway` 接口，不改应用服务主流程。

---

## 12. 阅读检查清单

改完或审查时，用下面几问过一遍：

1. 类名能否当目录用？是否超过 1000 行？新类是否在正确的 Maven 模块与包（`application` / `domain` / `infrastructure`）？
2. public 方法是否看签名就能调用？Javadoc / 注解属性说明是否完整（支付域是否含幂等）？
3. 非法参数与幂等是否在方法开头处理？
4. 复杂方法是否按 **§3.1** 分了功能块，且块说明能当「目录」读？
5. 状态迁移是否只经聚合根？金额是否统一为分？
6. gateway 是否只做接入，未嵌入领域规则？
7. 依赖是否仍单向（domain 不依赖 gateway；tools 不依赖 payment）？
8. 测试名能否当需求条目读？`mvn clean test` 是否通过？
9. 本次 diff 是否只做一件可概括的事？[`detail-design.md`](detail-design.md) / [`modules.md`](modules.md) 是否已同步？

任一项需要解释很久，就先改结构或改名，再继续加功能。
