# 设计原则规约

目标：设计与实现能对应到具体原则，审查时能说清「为何这样拆 / 不拆」。不为假想需求加抽象，也不把同一业务规则写两遍。

本规约管 **怎么拆、怎么复用、怎么分层**；「怎么写让人读懂」（命名、控制流、中文注释、功能块）见 [`方便人理解代码规约.md`](方便人理解代码规约.md)。两份都是强制标准，同一次提交内须一并满足。

适用范围：**mdyaipay** Maven 多模块工程（Java 17）。模块边界与职责见 [`modules.md`](modules.md)；领域与接口细节见 [`detail-design.md`](detail-design.md)。

**强制级别（MANDATORY）**：不是可选最佳实践。新功能、重构、Bug 修复须能对应到下文条文；无法说清拆/不拆理由的 diff 应退回。Cursor 持久规则：[`.cursor/rules/design-principles.mdc`](../.cursor/rules/design-principles.mdc)（`alwaysApply: true`）。

原则冲突时的优先级（本仓库约定）：**SOLID > KISS > DRY > SOC > YAGNI**。

即：冲突时**先**保证职责边界、依赖方向（D）、接口契约（L/I）与扩展点（O），**再**简化实现（KISS）、合并重复（DRY）、划清模块/层（SOC），**最后**才用 YAGNI 砍掉未入文档的需求。不得以「少写代码」为由破坏分层或开闭扩展。

---

## 1. SOLID（面向对象与依赖）

| 字母 | 原则 | 在本工程中的硬性要求 |
|------|------|----------------------|
| **S** | 单一职责 | 与可读性规约 **§1** 一致：一个 public 类型只做一件可一句话说清的事。`PaymentApplicationService` 编排收单，不写 JDBC；`MyBatis*Repository` 只做持久化，不含业务状态机。 |
| **O** | 开闭 | **对扩展开放、对修改关闭**：新渠道实现 `PaymentGateway` / 新压测协议实现 `LoadTestDriver`，**不**在应用服务里加 `if (channel == X)` 长链。必须改核心流程时，先在 `docs/` 说明扩展点为何不足。 |
| **L** | 里氏替换 | 接口的所有实现可互换且不破坏调用方假设：Mock 与真实 Gateway 契约一致；Repository 实现不返回「半初始化」聚合；子类/实现 **不加强** 前置条件、**不削弱** 保证（幂等、事务边界）。 |
| **I** | 接口隔离 | `mdyaipay-*-api` 的 Facade **小而专**（如 `UserFacade` / `AuthFacade` 分离），禁止「上帝接口」。模块内端口（`*Repository`、`*Gateway`）只暴露调用方需要的方法，不把 DAO 细节泄漏给 application。 |
| **D** | 依赖倒置 | **domain 定义端口**，infrastructure 实现；application 依赖 domain 接口，不 `new` 具体 MyBatis 类。依赖方向见可读性规约 **§1.2**：禁止 domain 依赖 gateway、tools 依赖 payment。 |

---

## 2. KISS（保持简单）

- 选 **当前问题最小** 的正确解法；优先平铺直叙的控制流（见可读性规约 **§4**），再考虑模式。
- 禁止「为模式而模式」：无多算法变体时不引入 Strategy 工厂树；无状态机规模时不引入重型状态框架。
- 配置与 API 表面：**能用一个布尔/枚举说清就不用嵌套 DTO**；Spring 配置项须有默认值，本地可零配置启动（与现有模块惯例一致）。
- 复杂度预算：若实现需向审查者解释超过 **3 层间接调用** 才能触达业务规则，应先简化或拆类型（可读性规约 **§1.1**）。

---

## 3. DRY（不要重复）

- **同一业务规则只写一处**：金额校验、幂等键解析、错误码映射 → `mdyaipay-tools-common` 或该模块 domain/`application` 内单一入口。
- **复制粘贴信号**：相同或近似逻辑出现 **≥ 2 处** 且无「故意隔离」文档说明 → 必须抽取；第 3 处出现视为审查缺陷。
- DRY **不** 等于「一个大 Utils 包打天下」：抽取后的 API 须符合 **S** / **I**；仅为两行且语义不同则 **不** 强行合并（避免错误抽象）。
- 测试可重复 Arrange 代码，但 **不断言重复的业务规则**；规则变更只改生产代码一处。

---

## 4. SOC（关注点分离）

- **Maven 模块 = 部署与领域边界**（可读性规约 **§1.2**）：gateway 只做接入与路由；payment 的 domain 不含 HTTP 状态码；user 的 Outbox 投递不嵌入支付收单规则。
- **包内三层**（application / domain / infrastructure）**不可混层**：Controller/Dubbo Provider 薄转调；领域规则不进 Filter（gateway 除外且仅限接入 concern）。
- **横切能力独立 artifact**：追踪（`tools-trace`）、耗时（`timetrace`）、压测（`loadtest`）**不** 反向依赖业务模块。
- 单文件内：**解析 → 校验 → 领域动作 → 持久化** 顺序可读；不要把 SQL 字符串与状态迁移写在同一方法块（用可读性规约 **§4.1** 功能块分开）。

---

## 5. YAGNI（你不会需要它）

- **不为未在 issue/设计文档中写明的「将来」** 预留接口、泛型参数、插件点或配置项。
- 禁止「先建空框架再填业务」：无第二个实现者时不写 `AbstractXxxService`；无第二种序列化格式时不写 `SerializerFactory`。
- 与可读性规约 **§12** 一致：修收单时不顺手重构代付；不引入与本次需求无关的依赖或模块。
- 若产品明确列入路线图，在 **`docs/` 设计** 中写清再实现；代码里不用 `// TODO 以后支持` 代替设计。

---

## 6. 提交前自检

1. 新类/接口是否 **一句话职责（S）**？依赖是否仍 **domain ← infrastructure（D）**？Mock 与真实实现是否 **可互换（L）**？
2. 扩展是否走 **Gateway / SPI / 新实现类（O）**，而非改应用服务核心？
3. Facade / 端口方法是否 **够小（I）**？gateway、tools 是否仍 **不承载领域规则（SOC）**？
4. 是否 duplicated 已有 tools-common / domain 规则（**DRY**）？实现是否 **够直（KISS）**？
5. 新增抽象是否 **已有第二个实现或调用方**？若无且非 SOLID 所必需，按 **YAGNI** 删除；diff 是否只做一件事？
